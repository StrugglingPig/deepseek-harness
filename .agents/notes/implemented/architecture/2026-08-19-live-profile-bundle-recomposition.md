# Agent Note: Plugin installs recompose the running profile bundle layer without restart

Status: implemented

English | [中文](2026-08-19-live-profile-bundle-recomposition.zh.md)

## Problem

Profile bundle layers were frozen at boot: `loadProfile` resolved `dsh.profile.bundles` once, so installing or removing a bundle — `dsh plugin add/remove`, dshmarket, a plugin-manager face, or a hand-edited manifest — needed a process restart before the host plane changed. dshmarket's hotMount softened this for pure-insert patches only: it mounts a copy under the market's own Include subtree, cannot express any other patch shape (its verdict falls back to "restart"), and the hot copy keeps running after the durable install lands, so the same package's host fibers run twice. On the browser side, client-hmr ignored `graph` frames: a new client row entered the served graph invisibly and needed a manual refresh.

## Decision

Live bundle-layer recomposition at the manifest seam, with a double-mount guard and browser entry-set propagation:

- **Layer re-resolution** (`@deepseek-ai/dsh-app-boot`): `resolveBundleLayers` was extracted from `loadProfile`, and `reloadProfileLayers` re-runs it per generation — heal the shared module fallback, re-read the manifest, re-resolve the layers. It does not read the user patch layer (the caller's `compose` closure owns that per generation) and never rewrites `cordis.yml` (a mid-run rewrite would trigger a redundant root-include refresh).
- **Manifest watching**: `watchProfileManifest` registers the profile `package.json` on the same Cordis HMR config-watch seam as `watchUserPatches`. The watched file is not parsed as a patch list — it is the JSON manifest a package manager rewrites; each change calls the caller's `compose()` and re-applies the full stack through `entry.update`, transactionally. A bounded retry (`attempts` × `delayMs`) self-heals a torn generation — the manifest rewritten before the package manager materialized a listed package — without a second file event; exhaustion falls back to the HMR service's loud `hmr/config-update-failed` broadcast with the last good tree still running. Native event delivery can also drop a rewrite entirely under heavy package-manager churn (FSEvents queue pressure), so a stat backstop (`pollMs`, default 2s) reconciles the manifest mtime and re-kicks the same serialized generation lane — events stay the low-latency path, the poll is the reliability floor. A request (event or poll) that lands while a generation is in flight is coalesced into one queued re-run: the in-flight generation may have read the manifest before the write, so dropping the request would lose the write forever (the 2026-08-20 review caught exactly this race; a regression test gates it).
- **Launcher generations re-derive everything** (`apps/cli` `composeLive`): bundle layers through `reloadProfileLayers`, both user patch files re-read fresh, and the derived overlays (the agent-presets shipped root and the telemetry switch) recomputed from that generation's own row index, so a bundle add/remove moves the rows they depend on. argv overlays stay frozen (argv is immutable), and each generation clones its patches to keep the include's insert-by-reference aliasing from baking overrides across generations.
- **Double-mount guard**: loader entry-id uniqueness is per tree, so a market hot row (a `mkt-` id under the market's own subtree) never collides with a recomposed durable row — but the package's host fibers would run twice. `duplicateSubtreeEntry` is the pure decision: the durable layer is exactly the root include's own subtree top level (every composed patch inserts there), and a CREATED fiber whose entry is not one of those top-level rows and whose `options.name` (the package name) matches a live, enabled durable row is flagged. Membership reads the top-level store, not a forest recursion — recursion would wrongly shield a hot mount's own nested rows. `installBundleLayerGuard` removes such a row as it appears (covers recomposition-lands-first); `disposeDuplicateSubtreeEntries` scans this loader's forest after each successful recomposition as the `afterUpdate` hook (covers hot-mount-lands-first there; a hot row in another loader realm is only reachable through the creation event). Entry-less fibers (preset subtrees, direct plugin mounts) and rows without a live same-name durable row (client-only shims) are never flagged; a failing removal warns instead of escaping.
- **Installation-authoritative resolution**: the same defect class that could dangle a live recomposition — a profile-hoisted copy of an in-box package shadowing the installation's own build, then pruned by an uninstall — is closed at every bare-name resolution site: the root include's imports (`builtins.include` carries the class, so every nested include tree inherits the ordering), the client table, and the agent-preset subtrees. The launcher provides `dshInstallAnchors` — the app's package.json plus every composed bundle's, tried in order, because no single one declares the whole in-box closure (the 2026-08-20 outage proved the single-anchor shape silently fell through to the config-directory walk for names the anchor did not carry, loading stale hoisted copies and splitting module identity: session creation then failed process-wide). In-box packages resolve from the running installation; the profile directory keeps only out-of-tree plugins. Hoisted copies left behind by older installs become inert — resolution bypasses them; no cleanup is required.
- **Browser entry-set** (`@deepseek-ai/dsh-client-hmr`): the node half subscribes to `clientModules.onGraphChanged` inside its `/plugins/events` effect and writes a fresh `graph` frame to every connection on each change; content-only rebuilds keep riding `rebuilt` frames. The browser half compares each frame's id set against the page's boot manifest (`window.__DSH_BOOT__`): an identical set cancels a pending reload, a differing set schedules `location.reload()` behind a 750ms debounce, re-checked at fire time and cancelled by a later frame that restores the boot set. A page without a boot manifest never reloads on frames.

## Alternatives considered

- **Keep the restart requirement**: rejected — immediate install-and-see is the feature; the hot-mount path proved the demand while covering only pure inserts and double-mounting.
- **Extend dshmarket's hotMount into the general mechanism**: rejected — hotMount is per-writer UI code expressing only pure inserts; the manifest seam covers every writer (CLI, market, plugin-manager, hand edits) with the full patch vocabulary, and makes uninstall a transactional dispose instead of a hand-rolled unmount.
- **Incremental browser mount/unmount without reload**: deferred. The boot kernel creates entries over the whole manifest behind a barrier and sweeps them to ACTIVE; incremental adoption needs module-system and kernel support the `graph` frame protocol can carry later. A single automatic reload is strictly better than the manual refresh it replaces.
- **Watch the profile `node_modules` instead of the manifest**: rejected — the manifest is the commit point writers agree on (the CLI writes the bundle list only after the package manager finishes); `node_modules` churn is noisy and mid-install. The torn generation the manifest ordering can produce is exactly what the bounded retry heals.

## Consequences

- Any manifest writer gets live host-side activation and transactional uninstall with no restart. The market's "restart" verdict for complex patches is now conservative: the host may already have applied live (a documented verdict mismatch, strictly better than promised).
- Hot-mount and durable layer coexist by rule — whichever lands second yields. Disposal is per-row and contained, so one broken hot row cannot fail the recomposition it follows.
- The browser reloads once per entry-set change; in-page plugin state is lost exactly as with the manual refresh it replaces, while content rebuilds keep the in-place hot swap.
- **Plugin updates (version bumps) still require restart**: Node's ESM import cache returns the already-imported module for the same resolved URL, so a recomposed row would mount stale code. Install/uninstall are the live paths by design; update stays restart-required.
- Retry is bounded and loud: a generation still failing after the retry budget surfaces through `hmr/config-update-failed` and leaves the last good tree serving.
